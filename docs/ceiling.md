# 천장 측정 (Ceiling Measurement)

> num_tasks=1 학습이 그룹 보상 ~-0.23(성공률 ≈38%)에서 정체한 원인을 가리기 위한 실험.
> **"과제가 구조적으로 어려운가" vs "RL이 못 배우는가"** 를 분리한다.
> 스크립트: [`ceiling_test/ceiling_sim.py`](../ceiling_test/ceiling_sim.py) · 결과 비교: [`RL_history.md`](RL_history.md)

---

## 1. 왜 이 실험을 하나

RL(MA-POCA)이 num_tasks=1에서 그룹 보상 ~-0.22(≈성공률 39%)로 정체했다. 원인 후보는 둘:

- **(가) 과제가 원래 어렵다** — 그렇다면 비-RL 정책(규칙 기반)도 비슷하게 낮아야 한다 → 과제·보상 재설계 필요.
- **(나) RL이 학습을 못 한다** — 그렇다면 규칙 기반은 훨씬 높아야 한다 → 탐색·크레딧·보상 shaping 문제.

이를 가르려면 **사람이 짠 정책의 성공률(=천장)** 을 알아야 한다. 그래서 게임 규칙을 충실히 재현하고
여러 정책의 성공률을 측정했다.

## 2. 왜 Unity가 아니라 파이썬인가

- Unity는 에디터 GUI 워크플로라 헤드리스로 수만 판을 빠르게 돌리기 번거롭다.
- 규칙(딜·follow-suit·로켓 트럼프·WinSpecificCard·드래프트)은 단순해 **순수 파이썬으로 충실히 재현 가능**하고,
  수만 판을 수초 내에 돌릴 수 있다.
- **한계**: 파이썬 재현은 Unity와 미세한 차이가 있을 수 있고, 협력 휴리스틱이 *증명된 최적*은 아니다.
  따라서 절대값은 ±몇 pp 오차 가능. 단 **구조적 결론**(아래)은 견고하며, 절대값 확정은 Unity rule-based
  시뮬(HeuristicOnly / `overrideMctsAssignee`)로 교차검증한다.

## 3. 재현한 게임 규칙 (Unity `TrickManager`/`MissionManager`와 동일)

- 카드 40장: 색 4종 × 1~9(=36) + 로켓 1~4(트럼프).
- 4인, 각 10장. 함장 = 로켓4 보유자, 함장이 첫 트릭 선.
- **follow-suit**: 리드 슈트가 손에 있으면 반드시 낸다. 로켓이 첫 카드면 로켓이 리드 슈트.
- **승자**: 로켓이 있으면 최고 로켓 / 없으면 리드 슈트 최고값. 승자가 다음 트릭 선.
- **과제(WinSpecificCard)**: 색 카드 1장(타깃)이 나온 트릭의 승자가 owner면 성공, 아니면 실패.
- **드래프트**: 함장부터 시계방향 take/pass. pass 허용 iff `남은 task T < 라운드 잔여 인원 R`,
  아니면 강제 take (모든 task 배정 보장).

## 4. 실험 설계 — 정책/조건

| 조건 | owner 선정 | 플레이 | 측정 의미 |
|---|---|---|---|
| **random** | 무작위 | 합법 카드 무작위 | 바닥선 |
| **coop + 랜덤 owner** | 무작위 | 협력 휴리스틱 | **RL이 도달해야 할 현실적 천장**(드래프트 나쁨) |
| **coop + 자기손패 드래프트** | `owner_score` 기반 take/pass | 협력 휴리스틱 | **부분관측에서 학습 가능한 현실 천장** |
| **coop + best-of-4 owner** | 4명 각각 시뮬 후 하나라도 성공 | 협력 휴리스틱 | **완전정보 구조적 천장**(상한) |

**협력 휴리스틱(은닉정보 — 각자 자기 손패+테이블+공개 owner/target만 사용)**
- owner: 타깃이 테이블에 오면 무조건 획득(최소 승리 카드). 타깃 보유 시 보존하다 마지막/강한 리드에 냄. 그 외엔 낮은 카드.
- 도우미: 타깃 보유 + owner가 이기는 중이면 릴리스, 아니면 보존. 타깃 미보유면 양보(낮은 카드, 타깃 트릭 안 이김).

**`owner_score(hand, target)` (자기 손패만으로 owner 적합도 추정)**
- `2.0·(로켓 수) + 0.2·(최고 로켓값)`
- 타깃 보유: `+ 1.0 + 0.4·(타깃 값)` (값 높을수록 자력 승리 쉬움)
- 타깃 미보유: `+ 1.2·(슈트 내 타깃을 이길 카드 수)`
- 드래프트: 점수 ≥ threshold면 take, 아니면 pass(마지막은 강제). threshold는 스윕으로 최적값 탐색.

**다중 task(N=1~4)**: N개 타깃을 드래프트로 배정 → 끝까지 플레이 → 타깃 출현 트릭마다 ±1,
**첫 실패 시 즉시 종료**. 이때의 **평균 그룹 리턴**이 곧 커리큘럼 `measure: reward`가 보는 값.

**규모**: 20,000 딜, `random.Random(42)` 고정 시드. 실행: `python ceiling_test/ceiling_sim.py 20000`.

## 6. 해석

1. **RL(38%) ≈ coop+랜덤owner(37.8%)** — RL은 **협력 플레이는 학습**했으나 **드래프트는 거의 랜덤.**
   트릭 플레이·관측 벡터·RL 학습능력 문제가 **아니다.**
2. **38→55 (+17pp) 는 자기 손패만으로도 가능** — 드래프트는 **학습 가능한** 레버. 지금 RL이 이걸 안 하고 있을 뿐.
3. **55→92 갭은 정책이 아니라 정보 문제** — 4명 패를 비교해 최적 owner를 골라야 가능. 단 **통신은 트릭 사이(플레이)
   에만 쓰고 드래프트엔 못 쓰므로**(코드 `CrewAgent.WriteDiscreteActionMask` 확인), 통신으로도 드래프트를 못 돕는다.
   → **55%가 부분관측 진짜 천장.**
4. **커리큘럼 임계값 버그**: 기존 yaml threshold 0.6/0.8/1.0 은 측정 천장(최대 0.23)을 **전부 초과 → 전 스테이지 도달 불가.**
   세 run(257/297/313)이 모두 같은 데서 정체한 원인. → Run4부터 0.05/0.0/0.05로 하향(`config/trainer_config.yaml`).
5. **measure=reward 는 잘못된 진급 지표**: N↑에 성공률(54→2.5%)은 폭락하는데 평균 리턴(0.087→0.231)은 오히려 상승
   (부분점수가 난이도를 가림). 비단조라 임계값 의미 부족.
6. **부수**: owner가 타깃 직접 보유(32%)가 도우미 보유(40%)보다 **더 어렵다**(저가 타깃은 자력 승리 곤란)
   → 저가 타깃은 보유자에게 배정하지 말 것(학습 가능 규칙). 단 RL 실측 지표는 부호가 반대라(success_by_assignee>helper)
   지표 정의/휴리스틱 차이 2차 확인 필요.

## 7. 결론 & 다음 단계

- **병목 = 드래프트 크레딧/보상.** 드래프트 전용 보상 신호가 없어(에피소드 끝 희소 ±1만) 정책이 드래프트를 못 배움 → 랜덤화 → 38%.
- **1순위 (B) 드래프트 보조 보상/크레딧**: 38→55를 여는 핵심. 드래프트 시점 신호 또는 owner 적합도 기반 shaping + 탐색 점검.
- **보류 (A) 보상 이진화**: N=1에선 이미 이진이라 정체와 무관하고, N≥2에선 보상을 희소화시켜 학습에 오히려 불리.
  커리큘럼 measure 문제는 별도(수동 lesson 제어 등)로 다룬다.
- **검증**: 위 적용 후 Group Reward가 -0.24 → 0(↑55% 천장) 쪽으로 움직이고 Lesson이 진급하는지 확인.
  Unity rule-based 시뮬로 절대값 교차검증.
