# MCTS 설계 노트 — 의사결정 기록 & 실험 로그

> 이 문서는 SpaceGent의 MCTS 협력 AI를 만들면서 내린 **결정의 근거**, **벤치마크 전체 수치**,
> **시도했다가 되돌린 실험과 그 이유**, 그리고 **게임 규칙 구현 범위**를 한곳에 정리한 것이다.
> 알고리즘 자체의 동작 설명은 [MCTS_Cooperative_AI.md](MCTS_Cooperative_AI.md)를 참고.
> (이 노트는 인수인계·발표·재현을 위해 로컬 메모리/세션에만 있던 분석을 저장소에 박제한 것이다.)

---

## 1. 확정된 튜닝값 (왜 이 값인가)

| 항목 | 확정값 | 근거 |
|------|--------|------|
| 알고리즘 | **SO-ISMCTS** (카드키 공유 트리) | 앙상블 PIMC의 strategy fusion·budget 분산 극복 |
| 탐색상수 **C** | **0.7** | 스윕 정점: 0.4=32.6%, **0.7=39.8%**, 1.0=33.5% |
| **budget** | **1000** | 1000 이후 성능 평탄(2000·8000 동일) → 병목은 탐색깊이 아님 |
| 재결정화 **K** | **5** (RedeterminizeEvery) | 매 iteration 재샘플은 과비용, 5회당 1회가 다양성·속도 균형 |
| determinizations | 10 | 불완전정보 분산 감소, 이 이상은 한계효용 낮음 |
| 롤아웃 정책 | **능동 feeding 포함 협력 롤아웃** | 성능의 대부분이 여기서 나옴(아래 참조) |

**핵심 발견:** budget을 올려도 성능이 안 오른다(평탄). 즉 **품질 천장은 "얼마나 깊이 탐색하느냐"가 아니라
"시뮬레이션(롤아웃)이 얼마나 협력적으로 잘 두느냐"**다. → 레버는 트리 깊이가 아니라 롤아웃 정책.

## 2. 벤치마크 전체 수치

### 2-1. 단일 태스크 (담당자가 자기 타깃 보유, Phase1, 400에피소드)

- **MCTS 46.5% vs RuleBased 23.5%** → 약 2배 우월, 전 값 구간에서 우세.
- **타깃 값별 구조적 천장**: v1~3 ≈ 10~25%, v5 ≈ 36%, v9 ≈ 95% (값↑일수록 쉬움).
  - 담당자만 그 카드를 낼 수 있어, 낮은 값 타깃은 트릭 승리가 본질적으로 어려움 → **협력 불가 시나리오**.
- budget 500→4000 올려도 성공률 불변 → 단일태스크 천장은 탐색이 아니라 **카드 분포의 한계**.

### 2-2. 다중 태스크 협력 (owner-held, 표준 비교)

| 시나리오 | MCTS 미션 | Rule 미션 | MCTS 완수 | Rule 완수 |
|----------|-----------|-----------|-----------|-----------|
| 4-task (budget 2000/det20) | 2.3% | 0% | 24.4% | 9.0% |
| **2-task (budget 1000/det10)** | **19.7%** | 5.5% (3.6배) | **36.2%** | 17.0% (2.1배) |

- 4-task는 전부-아니면-전무라 신호가 약함 → **2-task가 최적화 sweet-spot**.
- budget 일찍 포화(2000→8000 평탄).

### 2-3. 협력 목표 시나리오 (cooperativeTargets=ON, 목표를 전체 덱서 무작위)

타깃을 owner 손이 아니라 전체 덱에서 뽑음 → 동료가 타깃 보유(helper-held) 발생 → **실질 협력 필요**.

| 정책 | 미션 성공 | 완수율 |
|------|-----------|--------|
| MCTS (능동 feeding 전) | 29.5% | 46.8% |
| **MCTS (능동 feeding 후, 800미션)** | **34.6%** (+5.1pp) | **49.9%** (+3.1pp) |
| RuleBased | 6.7% | 19.0% |
| **격차** | **약 5배** | **약 2.6배** |

- **낮은 값 구조적 천장 사라짐**: 값1 타깃 owner-held 8% → 협력 시나리오 34%.
- 타깃 보유자별: **helper-held 52% > assignee-held 39%** (동료가 유연히 흘려주면 더 쉬움).
- 값별 완수 평탄·높음(44~60%). 2-task는 거의 독립(feeding이 디커플) → 미션 ≈ 완수².
- 협력 시나리오에서도 budget 평탄(1000≈3000) → 레버는 역시 롤아웃 협력 정책.

## 3. 시도했다가 되돌린 실험 (negative results)

> "직관이 아니라 측정으로 정했다"의 증거. 발표에서 신뢰도를 높이는 부분.

| 실험 | 의도 | 결과 | 왜 실패 |
|------|------|------|---------|
| **엔드게임 완전탐색** | 종반을 정확히 풀어 최적화 | 오히려 악화 → 제거 | **strategy fusion**: 결정화별 정확값을 평균내니 "실제론 남의 패를 안다"는 비현실적 낙관 편향 |
| **셋업(stall) 플레이** | owner가 stall로 트릭 확보 | 악화 → 제거 | owner가 트릭을 가져가려 stall하면 동료가 목표 무늬를 리드하게 되어 **가로채기(interception)** 유발 |
| **feeding 우선순위 조정** (약한 승리카드 먼저) | 강패 보존 | 소폭 하락 → 원복 | 단순 처리 순서가 미세하게 더 나음(900미션 기준) |
| **owner-held 천장 돌파 시도** (budget/C/엔드솔버/stall 전부) | 39% 넘기 | 모두 실패 | owner-held 39%는 **구조적 천장**. 천장 짜기보다 협력 시나리오(helper-held)가 정답 |

**교훈:** owner가 자기 약한 타깃을 직접 들고 있으면 누구도 도울 방법이 없다(구조적). 능동 feeding이 푸는 건
**"내 타깃이 동료 손에 갇힌 경우"**뿐이다. 그래서 협력 시나리오에서 천장이 뚫린다.

---

## 4. 능동 feeding이 푸는 것 / 못 푸는 것 (중요 구분)

임무 = "지정 카드가 든 트릭을 **임무 주인**이 이긴다". **임무 주인 ≠ 카드 소유자**일 수 있다.

| 상황 | feeding으로 해결? | 이유 |
|------|------------------|------|
| 내 임무 카드가 **동료 손**에 있음(약한 값) | ✅ 가능 | 내가 그 무늬 무적패를 리드 → 동료가 그 카드를 내 승리 트릭에 흘림 → 내가 완수 |
| 내 임무 카드를 **내가** 들고 있는데 약함 | ❌ 불가능 | 한 트릭에 카드 1장. 약한 카드로는 못 이기고, 남이 날 이기게 만들 방법도 없음 |

> 완수하는 주체는 **언제나 임무 주인**. 동료는 카드를 배달하는 역할.
> 코드: `MCTSRollout.TryLeadToFeedTeammate`(미끼 리드) ↔ `TryReleaseTeammateTarget`(동료의 배달)이 짝.

## 5. 게임 규칙 구현 범위 (스페이스 크루 50미션)

### ✅ 완전 구현 + enforce (실게임 + MCTS 시뮬 공통)
- 트릭 테이킹 전체(follow-suit, 로켓 트럼프, 승자 판정) — `MissionRules.Beats`
- 태스크(WinSpecificCard) 완수/실패, 사령관부터 드래프트(가져가기/패스 `T<R`)
- **순서 토큰 전 종류**: N1~N5(순번), Ω(전부 끝난 뒤), 화살표 1~4(체인) — `MissionManager.IsOrderTokenValid` + MCTS `MCTSState.IsOrderValid`
- **통신 토큰**: 1회/트릭사이/로켓제외, 데드존(위치숨김)·통신차단⚡N·특정인금지(M11). 공개카드는 MCTS 결정화 제약(`commReveals`)으로 반영
- 조난신호: 인접 전달(단, **AI/배치는 자동 스킵** → 학습·MCTS 미사용)
- 전역규칙 트릭단위: NoNineWins(M16,17), BalanceTricks(M29,34), RocketsInOrder(M44)
- 전역규칙 핸드종료: CommanderFirstAndLast(M34), OmegaOnLastTrick(M48), AllRocketsMustWin(M13)
- 첫 트릭 후 카드교환 CardExchange(M12)
- 미션 1~50 코드 정의(`MissionDatabase.BuildAllMissions`)

### ⚠️ 정의됐으나 근사/간소화 (정확도 주의)
- **RocketOneWinsTwice(M26)**: "로켓1 한 번이라도 냈으면 통과"로 간소화. **실제 규칙 문구는 `the_crew_missions_ko.md` 원문 확인 필요**(카드 1장이 2번 이기는 게 아님 — 횟수형 전역조건으로 재해석해야 함).
- **AllRocketsMustWin(M9,13)**: "로켓이 트릭을 이겼는가"가 아니라 "플레이됐는가"만 체크 → 느슨. M9는 원래 로켓1 전용인데 편의상 공유.

### ❌ 데이터만 있고 메커니즘 미구현 (실제 동작 안 함)
- **CommanderDecision(M5,20,27,33,37,41)**: 사령관이 한 명에게 태스크 몰아주기 — 드래프트 로직 없음, 일반 드래프트 폴백
- **CommanderDistribution(M24,32,36,43)**: 사령관이 태스크 1장씩 공개 배분 — 미구현, 일반 드래프트 폴백
- **TokenTransferAllowed(M23,40)**: 순서 토큰 이동 — 플래그만, 기능 없음
- **OnePlayerFirstFourOnly(M50)**: enum 정의만, `OnHandEnded` 판정 switch에 케이스 없음 → 미검증 통과
- **LeftOfPinkNineWinsAllPink(M46)**: 동일 — 판정 누락

> 미구현 4종(사령관 결정/분배)은 **드래프트 구조 자체가 바뀌는** 규칙이라 별도 설계 필요(RL 전이로도 어려운 부류).
> M46·M50은 핸드종료 판정만 추가하면 됨(전역규칙 switch에 케이스 추가).

## 6. 평가 노브 위치 (재현 시 필수)

모든 평가 설정은 **GameManager 인스펙터**에 있다 (MissionManager 필드는 씬 미직렬화라 무시됨):

| 필드 | 표준 벤치마크 값 |
|------|-----------------|
| `aiPolicy` | MCTS |
| `cooperativeTargets` | true (협력 시나리오) |
| `overrideNumTasks` | 2 |
| `mctsBudget` | 1000 |
| `mctsDeterminizations` | 10 |
| `evaluationLogging` | true |

EvalStats가 미션 성공률 + 평균 완수율을 콘솔에 누적 출력. 정책 라벨 바뀌면 자동 리셋.

## 7. 다음 큰 도약에 필요한 레버 (순수 튜닝의 한계)

budget/C/엔드솔버/stall 등 **순수 MCTS 튜닝은 모두 천장에 부딪혔다**(구조적). 더 올리려면 새 레버가 필요:
- 학습된 롤아웃 정책 / value network (현재는 휴리스틱 롤아웃)
- 더 정교한 신념 추론(상대 모델링)
- 또는 RL 에이전트와의 대결/혼합

현재 베이스라인: **협력 2-task 기준 완수 ~50% / 미션 ~35%, RuleBased 대비 완수 2.5배.**
